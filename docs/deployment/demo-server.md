# Демо-стенд на сервере

Стенд показывает платформу на **вымышленном демо-мире** (Д-2) с быстрым входом под персонажами (Д-5). Это не продакшен: реальные данные сюда не вносить.

| | |
|---|---|
| Сервер | AWS EC2 `35.88.203.152` (Ubuntu 26.04, ARM64, 2 ядра, 8 ГБ), SSH: `ssh aws-bz` |
| Адреса | **`https://team.bunaziua.org`** — домен организации (A-запись на IP стенда, обычный сертификат Let's Encrypt; с этого адреса панель ставится как приложение — PWA); **`https://35.88.203.152`** — по IP (полноценный сертификат); `http://35.88.203.152` и `http://ec2-35-88-203-152.us-west-2.compute.amazonaws.com` — без шифрования |
| Каталог | `/opt/bz-crm` — код из git (без истории), `.env` стенда |
| Защита | нет: по решению заказчика стенд открыт всем, кто знает адрес; быстрый вход доступен любому |

## Как устроено

`deploy/demo/compose.yml` — те же контейнеры, что локально (`app`, `queue`, `scheduler`, `reverb`, `nginx`, `mysql`, `redis`), плюс **Caddy** — единственный, кто открыт наружу (порты 80 и 443):

- выпускает и продлевает сертификат Let's Encrypt **на IP-адрес** (короткоживущий, около 6 дней; продлевает сам). Браузер не сообщает имя сайта при обращении по IP, поэтому этот сертификат отдаётся по умолчанию (`default_sni`);
- по IP отвечает и по обычному HTTP — это работает при любой судьбе сертификатов;
- имя Amazon обслуживает только по HTTP: Let's Encrypt по своей политике не выдаёт сертификаты на имена `*.amazonaws.com` (ответ `rejectedIdentifier`), обойти это нельзя. Для HTTPS по имени нужен свой домен с A-записью на `35.88.203.152` — тогда достаточно вписать его в `Caddyfile`;
- `/app/*` (WebSocket мессенджера) отдаёт в Reverb, всё остальное — в nginx.

MySQL, Redis, nginx и Reverb наружу не открыты. WebSocket браузер открывает на `wss://35.88.203.152` (`REVERB_CLIENT_HOST`).

nginx спрашивает адрес контейнера PHP у DNS Docker при каждом запросе: после перезапуска контейнер может получить другой адрес, и запомненный при старте давал бы 502. Приложение доверяет заголовкам прокси (`TRUSTED_PROXIES=*`) — иначе на HTTPS-странице оно строило бы http-ссылки на стили и скрипты.

Отличия от локальной среды: `APP_ENV=demo`, `APP_DEBUG=false`, письма уходят через **Mailgun** (`MAIL_MAILER=mailgun`, домен `mg.ttl10.net`, отправитель `no-reply@mg.ttl10.net`; ключ — общий ключ ваших проектов, лежит только в `.env` стенда). Письма на вымышленные адреса демо-мира (`@demo.bz-crm.test`) приложение не отправляет никогда — их отсекает `DropFictionalRecipients`; уходят только письма людям, зарегистрировавшимся с настоящим адресом. `init-env.sh` создаёт новый стенд с `MAIL_MAILER=log` — Mailgun подключается вписыванием `MAILGUN_DOMAIN`, `MAILGUN_SECRET` и `MAIL_MAILER=mailgun`; фронтенд собран (`npm run build`), а не отдаётся dev-сервером, процессы PHP работают от `www-data`. Антивирус выключен (Д-28), Playwright и ClamAV на стенде не ставятся.

**Что работает только по HTTPS.** Приложение агитатора без сети (service worker) и передача местоположения требуют защищённого адреса: по `https://35.88.203.152` они работают, по обоим HTTP-адресам — нет.

## Обновить стенд

С рабочего ПК, из каталога проекта:

```bash
git archive --format=tar HEAD | ssh aws-bz 'tar -x -C /opt/bz-crm --exclude=storage --exclude=bootstrap/cache'
```

```bash
ssh aws-bz '/opt/bz-crm/deploy/demo/deploy.sh'
```

Первая команда переносит закоммиченный код (без `.env`, без истории; удалённые из git файлы на сервере остаются). `storage/` и `bootstrap/cache/` пропускаются: ими владеет приложение (`www-data`), в git там только пустые `.gitignore`. Вторая ставит зависимости, собирает фронтенд и применяет миграции; данные стенда сохраняются. `deploy.sh --fresh` — то же, но демо-мир строится заново (около минуты; всё, что сделано на стенде руками, пропадает).

## Обслуживание

```bash
ssh aws-bz
cd /opt/bz-crm
./deploy/demo/dc ps                       # состояние контейнеров
./deploy/demo/dc logs -f --tail=100 app   # журнал PHP; caddy — сертификаты
./deploy/demo/dc exec -u www-data app php artisan …
```

`.env` стенда создан один раз скриптом `deploy/demo/init-env.sh` со случайными секретами (ключ приложения, пароли БД, ключи Reverb, общий пароль персонажей) и больше не перезаписывается. Читать его могут только приложение и пользователь `ubuntu`. Общий пароль демо-персонажей — `DEMO_USER_PASSWORD` в этом файле; для быстрого входа он не нужен.

Контейнеры перезапускаются сами после перезагрузки сервера (`restart: unless-stopped`, Docker включён в автозапуск).

## Проверить стенд в браузере

Браузерные тесты (Playwright) запускаются с рабочего ПК прямо против стенда:

```bash
docker compose --profile e2e run --rm -e E2E_BASE_URL=https://35.88.203.152 e2e
```

Проверяются офлайн-приложение агитатора (service worker, очередь, повторная отправка без дублей), подключение мессенджера по WebSocket и карта. Тест записывает визиты в демо-мир стенда — после него мир стоит пересобрать: `./deploy/demo/dc exec -u www-data app php artisan migrate:fresh --seed --force`.
