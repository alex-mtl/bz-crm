# ADR-003: Архитектура авторизации

- **Статус:** принято (2026-09-30, начало фазы 1). Реализация: фаза 1 — коды, роли, deny, «свои объекты», жёсткие ограничения; фаза 2 — области по территориям и оргструктуре, поля, делегирование
- **Дата:** 2026-09-30
- **Источник:** ТЗ §14–16, §52, §64, §71; ФО §3.1, §3.5, §6.2, §6.3, §8

## Требования

- Разрешения вида `модуль → объект → поле → действие`.
- Области действия: организация / регион / подразделение / группа / свои / подчинённые.
- Временные роли и делегирование с автоотзывом; наследование ролей; `deny` перекрывает `allow`.
- Симулятор прав «глазами роли».
- Одна точка проверки для Web, Livewire, Filament, API, поиска, отчётов, экспорта, джобов, уведомлений, вебхуков, фоновых процессов (ТЗ §15).
- Конфиденциальные слои профиля — отдельные сущности со своими политиками, каждый доступ логируется (ТЗ §16).
- Новый модуль или тип данных не требует изменения кода подсистемы прав (ФО §3.5).

## Предлагаемое решение

1. Единая точка входа — доменный сервис `Access\AuthorizationService`:
   `can(User $user, string $permission, ?object $subject = null): bool`
   и парный для списков — применение scope к запросу (`scopeQuery(User, permission, Builder)`), чтобы фильтрация шла в SQL, а не после загрузки.
2. Laravel Gates/Policies и Filament вызывают этот сервис и не содержат собственной логики доступа (ТЗ §64).
3. Хранение ролей и разрешений — таблицы по ТЗ §14: `roles`, `permissions`, `role_permissions`, `user_roles`, `role_scopes`, `permission_scopes`, `delegations`.
4. Разрешения описываются декларативно: каждый модуль регистрирует свой каталог кодов (`people.read`, `people.export`, …). Автотест проверяет, что каждый код назначен хотя бы одной роли (ФО §6.2).

## Модель решения (Д-17, 2026-09-30)

Доступ не бинарный. Каждая проверка — пересечение слоёв:

```
разрешено = код разрешения у одной из действующих ролей (роли, делегирования, временные роли)
          ∧ объект в области действия роли: организация / территории (Д-3) / подразделение / свои / по связи
          ∧ правила объекта: членство, авторство, видимость, связь «начальник» (Д-11), статус объекта
          ∧ для полей: права на группу полей ∧ выбор владельца (Д-13)
          ∧ нет явного запрета (deny перекрывает allow)
```

Поверх — жёсткие ограничения, которые никакая роль не отменяет: тот, о ком заметка «360», её не видит (Д-14); заявитель на рассмотрении не получает внутренних данных; счётчики не раскрывают недоступное (ТЗ §67).

Каталог кодов со слоем данных для каждого кода — [`docs/security/permission-catalog.md`](../security/permission-catalog.md). Для списков слой данных применяется в SQL через `scopeQuery`, а не фильтрацией после загрузки.

## Открытый вопрос: Spatie Laravel Permission

ТЗ §71 относит `spatie/laravel-permission` к одобренным строительным блокам. Этот пакет покрывает хранение ролей и разрешений и их проверку, но **не покрывает** scopes по оргструктуре, разрешения на уровне полей, явный `deny`, временные роли и делегирование — а это ядро требований ФО §6.2.

Варианты для решения в фазе 1:
- **A.** Spatie как слой хранения ролей и разрешений, а scopes, deny, делегирование, поля — собственным кодом в `AuthorizationService`.
- **B.** Собственная модель целиком по ТЗ §14, без Spatie.

**Решение (T1) — B**, собственная модель без Spatie: при варианте A на пакет ложится только тривиальная часть, но вся модель данных ролей завязывается на его схему, а конфликтующие семантики (например, `deny`) пришлось бы строить в обход него. Решение принимается в начале фазы 1 после оценки по ТЗ §70.

## Последствия

- Скрытие кнопки никогда не считается проверкой прав (ТЗ §15).
- Матрица тестов «A видит X / B не видит X ни через API, поиск, экспорт, счётчики» (ТЗ §52) обязательна для каждого чувствительного модуля.
