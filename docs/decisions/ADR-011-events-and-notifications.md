# ADR-011. Мероприятия и центр уведомлений

**Статус:** принято (фаза 5, 2026-10-01)
**Контекст:** ФО §5.3, §6.7, §6.13; ТЗ §22, §37, §68; Д-1, Д-3, Д-17, Д-23, Д-24; каталог прав §7.

## 1. Мероприятия

**Видимость** — как у постов ([ADR-010](ADR-010-social-visibility-groups-api.md)): `Events\EventVisibility::visibleTo(User)` — единственный SQL-источник. Уровни: вся организация / территории (в обе стороны по дереву) / группы / только приглашённые. Организатор и **каждый приглашённый видят мероприятие при любом уровне** — приглашение и есть «явно открытое». Так же его видят **те, кто отвечает за организатора по роли** (Д-24): руководитель подразделения, региона, организации, суперадмин — в области своей роли. Список, календарь, `.ics`, iCal-фид, уведомления и дайджест начинают с `visibleTo()`.

**Кто что проводит** (каталог §7): сотрудник — закрытые мероприятия и мероприятия своих групп; руководитель — мероприятия для территорий своего доступа; руководитель организации — для всех. Админ группы проводит мероприятие группы и без системного права.

**Видеть и управлять — одна область (Д-24).** Организатор управляет своим мероприятием по связи. Руководитель видит и меняет мероприятия людей своей области (локатор по организатору, код `events.update`) при любом уровне видимости, включая закрытые и мероприятия групп, где он не состоит; суперадмин — все. Руководитель другого подразделения закрытое мероприятие не видит и не меняет, даже если его пригласили: приглашение даёт видимость, но не управление.

**Участники.** `event_attendees` связывает мероприятие с **человеком** (`Person`), а не с учётной записью: приглашён, ответил («иду / интересует / не иду» с комментарием), был ли на месте. Отметить присутствующим можно и сторонника без учётной записи. Отметка порождает доменное событие `AttendanceMarked`; CRM по нему ведёт факт «посещение мероприятия» в ленте человека (ФО §5.3) — сегмент «был на N мероприятиях» считает именно эти факты.

**Повторяющиеся мероприятия** — серия обычных мероприятий с общим `series_id`, создаётся сразу до даты окончания (не больше 60 повторов). У каждого повтора свои ответы, отметки и напоминания; изменение и отмена — «только это» или «это и следующие».

**Напоминания** — строки `event_reminders` (за сколько минут, когда напомнить). Планировщик `events:tick` раз в минуту отправляет наступившие тем, кто ответил «иду» или «интересует». Отправку «захватывает» `UPDATE … WHERE sent_at IS NULL`: повторный или параллельный запуск ничего не отправит дважды.

**Календари** (ТЗ §22 — только экспорт): ссылка «Добавить в Google Calendar», файл `.ics`, iCal-фид. Фид — секретный адрес (в базе только хеш токена, показывается один раз, отзывается) для личного календаря, территории или группы; при каждом чтении показывает то, что его владелец видит сейчас. Двусторонней синхронизации нет.

**Итоги** — текст, файлы и фотоотчёт после начала мероприятия; файлы — на закрытом диске, отдаются тем, кто видит мероприятие.

## 2. Уведомления

**Категории** регистрируют модули (`NotificationCategories`): задачи, CRM, группы, лента, решения модераторов, мероприятия, напоминания, объявления, критичные, безопасность, дайджесты. У категории — каналы по умолчанию и признак «обязательная».

**Каналы:** в системе (колокольчик и центр уведомлений) и email. **Push отложен (Д-23):** столбец в настройках есть, доставки нет.

**Настройки.** Канал включён, если: так решил сам человек → иначе так задано умолчанием хотя бы одной из его ролей → иначе так задано категорией. Обязательные категории (безопасность, критичные, решения модераторов) настройкам не подчиняются.

**Одна реализация для всех уведомлений** — трейт `RoutesByPreference`: класс называет категорию и строит полезную нагрузку для колокольчика; каналы выбирает `Preferences`, а письмо строится из той же нагрузки — поэтому письмо не может сказать больше, чем колокольчик. Текст — на языке получателя (`User::preferredLocale()`).

**Уведомление не раскрывает недоступное (ТЗ §37)** — три заслона:
1. отправляется только тем, кто видит предмет (решает модуль-отправитель через свою видимость);
2. перед доставкой из очереди проверяется ещё раз (`shouldSend`): если доступ пропал, пока уведомление ждало, — не доставляется;
3. если доступ пропал после доставки (приглашение отозвано, пост скрыт или сужена аудитория, человек исключён из секретной группы) — `Retraction` опустошает сохранённое уведомление: остаётся факт «содержимое больше недоступно», без названия и ссылки. Для этого уведомление хранит категорию и предмет в собственных колонках.

**Объявления** — получателям в области отправителя (кто вне области — молча не получатель). **Критичное** (СБ, руководитель организации, суперадмин) идёт всем получателям по всем каналам, висит полосой на каждой странице, пока человек не нажмёт «Подтвердить прочтение»; «прочитать всё» его не закрывает. Кто подтвердил — видят отправитель и держатели права на критичные уведомления.

**Дайджесты** — ежедневный и еженедельный. Содержимое дают секции модулей (новые посты, ближайшие мероприятия, свои задачи); каждая секция запрашивает данные через видимость своего модуля от имени читателя. Строка `notification_digests` с уникальным ключом (человек, частота, период) — «захват»: повторный запуск за тот же период ничего не отправит. Пустой дайджест не отправляется.

## 3. Что отложено

| Что | Куда |
|---|---|
| Push (Web Push или нативные приложения) | после решения по мобильным клиентам (Д-23, ФО §12 вопрос 6) |
| Двусторонняя синхронизация с Google Calendar | только по отдельному решению заказчика (ТЗ §22) |
| Отметка посещения по QR | ФО называет её необязательной |
| Упоминания `@` как событие уведомлений | фаза 6 (мессенджер) |
| Шаблоны писем, редактируемые администратором | фаза 9–10 |
| Гео-точка мероприятия на карте панели | фаза 7 (сейчас — координаты и ссылка на карту) |
