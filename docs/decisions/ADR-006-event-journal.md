# ADR-006: Журнал событий в ядре платформы

- **Статус:** принято (2026-09-30, начало фазы 1)
- **Дата:** 2026-09-30
- **Источник:** Д-4 ([`requirements-addendum.md`](../requirements-addendum.md)); ТЗ §17, §44, §49–50, §57, §71; ФО §3.1, §6.3.4, §6.16

## Контекст

Заказчик требует гибкий журнал событий в ядре с самого начала реализации (Д-4). Журнал фиксирует любое действие, включая назначение прав и доступ к конфиденциальным слоям. Он append-only и доступен только по отдельной привилегии.

Это **бизнес-журнал**, отдельный от технических логов приложения (`storage/logs/app.json.log`, фаза 0).

## Предлагаемое решение

### Модель записи

| Поле | Назначение |
|---|---|
| `id`, `occurred_at` | идентификатор и момент события (UTC, микросекунды) |
| `event_type` | код из каталога: `auth.login.failed`, `access.territory.granted`, `profile.hr_layer.viewed`… |
| `category` | безопасность / доступ / изменение данных / бизнес-событие / администрирование / интеграции |
| `severity` | info / notice / warning / critical |
| `actor_type`, `actor_user_id`, `actor_person_id` | пользователь, система, задача очереди, автоматизация, AI |
| `acting_as` | собственные права / делегирование (ссылка на делегирование) / имперсонация |
| `subject_type`, `subject_id` | объект действия (полиморфно) |
| `old_values`, `new_values` | изменения; секреты и чувствительные поля маскируются по правилам типа события |
| `context` | произвольные данные типа события (JSON), например причина выдачи прав |
| `ip_address`, `user_agent`, `request_id` | источник |
| `correlation_id` | связывает все записи одного действия, включая порождённые им задачи очереди |

### Каталог типов событий

- Каждый модуль регистрирует свои типы событий в своём сервис-провайдере: код, категория, важность, правила маскировки, ключи переводов для описания на ro/ru/en.
- Запись события незарегистрированного типа — ошибка (ловится тестами), чтобы каталог оставался полным.
- Автотест: для каждого типа из каталога есть переводы на три языка.

### Способ записи

- Одно API ядра: `Audit\EventJournal::record(EventType, subject, changes, context)`.
- Доменные Actions вызывают его явно, либо слушатель доменных событий (ТЗ §44) превращает событие в запись.
- **Запись идёт в той же транзакции БД, что и действие.** Откат действия откатывает запись; изменение без записи невозможно.
- Контекст (актор, `acting_as`, IP, `request_id`, `correlation_id`) собирается автоматически: middleware для HTTP; передача в payload задач очереди для фоновых процессов.

### Неизменяемость

- Модель журнала запрещает `update`/`delete` на уровне приложения; это покрыто тестами.
- На уровне БД — один из вариантов, выбор в фазе 1:
  - **(а)** отдельный пользователь MySQL для production с правами `INSERT`/`SELECT` на таблицу журнала без `UPDATE`/`DELETE` — инфраструктурная настройка, не SQL-код;
  - **(б)** триггеры, блокирующие `UPDATE`/`DELETE`. Это БД-специфичный код, поэтому только изолированно в миграции и с документированием по ТЗ §4, §81.
- **Решение — (а)**: отдельный пользователь MySQL без `UPDATE`/`DELETE` на таблицу журнала настраивается при развёртывании production; в приложении — запрет через модель и тесты.
- Единственный путь удаления — очистка по сроку хранения отдельной командой под отдельной привилегией. Факт очистки сам фиксируется в журнале.
- Опционально, по решению позже: хеш-цепочка записей для обнаружения подделки.

### Хранение и производительность

- Сроки хранения — по категориям, настраиваются суперадмином.
- Индексы: `(subject_type, subject_id, occurred_at)`, `(actor_user_id, occurred_at)`, `(event_type, occurred_at)`, `(correlation_id)`.
- Высоконагруженные «шумные» события (например, логирование каждого просмотра, если его включить) могут писаться асинхронно через очередь. Это явно помечается в каталоге и не применяется к событиям безопасности, доступа и изменения данных.

### Просмотр

- Интерфейс в Filament: фильтры по актору, типу, категории, объекту, периоду, корреляции; история объекта; история действий человека.
- Выборка идёт через `AuthorizationService`: привилегия `audit.read` плюс область действия. Например, руководитель региона может видеть журнал только по своему региону, если ему это разрешено.
- Сам просмотр журнала и экспорт логируются. Экспорт — отдельная привилегия.

## Оценка `spatie/laravel-activitylog` (ТЗ §70, §71)

Пакет одобрен ТЗ как строительный блок и хорошо логирует изменения моделей: `causer`, `subject`, `properties`.

Не покрывает из коробки:
- каталог типов с категориями, важностью и переводами;
- `acting_as` (делегирование и имперсонация);
- сквозную корреляцию с задачами очереди;
- маскировку по правилам типа события;
- неизменяемость — модель `Activity` можно менять и удалять, а команда `activitylog:clean` удаляет записи без собственного следа.

**Варианты** (решение T6 в [`open-questions.md`](../open-questions.md)):
- **A.** Activitylog как хранилище, остальное — надстройкой.
- **B.** Собственный модуль `Audit` по схеме выше.

**Решение (T6) — B**, собственный модуль `Audit`. Большая часть требований Д-4 лежит вне возможностей пакета. При варианте A пришлось бы обходить его модель и команду очистки, а выигрыш свёлся бы к небольшому объёму кода записи изменений.

## Последствия

- Любое новое действие в любом модуле считается незавершённым без записи в журнал — это часть Definition of Done.
- Демо-мир (Д-2) порождает реальные записи журнала через те же Actions, поэтому журнал в демо сразу наполнен осмысленной историей.
