# ADR-012. Мессенджер: доступ к чатам, real-time, антивирус

**Статус:** принято (фаза 6, 2026-10-02)
**Контекст:** ФО §6.6; ТЗ §20–21, §37, §59, §70–71; Д-17, Д-26, Д-27; каталог прав §8; вопрос T2.

## 1. Кто читает чат

Чаты трёх типов: личный диалог, групповой чат, обсуждение объекта (задача, проект, группа).

- **Диалог и групповой чат читают только участники.** Никакая роль — включая суперадмина и руководителя — чат не открывает: область роли к чатам не применяется.
- **Обсуждение объекта читает тот, кто вправе читать объект.** Правило даёт модуль объекта через реестр `Messaging\ChatSubjects` (доступ, название, ссылка); Messaging о задачах, проектах и группах не знает. Чат секретной группы не существует для тех, кто вне группы.
- Единственный источник — `Messaging\ChatAccess` (`chatIdsFor`, `mayRead`, `mayWrite`, `canManage`, `canModerate`, `mayMentionAll`). Список чатов, сообщения, поиск, вложения, уведомления, каналы WebSocket начинают с него.
- **Роль в чате** (владелец / админ / модератор / участник) — не системная роль. Состав, роли, ссылки и закрепление — владелец и админ; удаление чужих сообщений — ещё и модератор; `@all` — владелец и админ чата либо системное право `messages.mention_all`, но только в чате, где человек участник.
- **Чтение без участия** — зарезервированное право `chats.read.investigation` 🔒: не выдано никому, выдаётся явно на роль, требует причину, каждое открытие — запись в журнале (`messaging.chat.investigated`).

**Кто кому может написать первым (Д-26).** Диалог создаётся, если отправитель видит получателя (`people.read`) и таблица `direct_message_rules` это разрешает: у отправителя должна быть роль, которой разрешено писать каждой из ролей получателя. Стартовые значения: кандидат не пишет первым никому, остальные — всем. Ответить в существующем диалоге можно всегда. Таблица меняется в панели (`messaging.policies.manage`), изменение — в журнале.

Чтобы волонтёр мог написать своему руководителю, в общее правило `people.read` добавлена связь: **каждый видит карточки своей цепочки начальников** (непосредственный начальник и все выше). Это расширение видимости людей, а не только мессенджера.

## 2. Модель сообщений

- **Ветки** — дерево по `parent_id` с `root_id` и `depth`; предел глубины — `messaging.max_thread_depth` (12): ответ глубже остаётся на последнем уровне.
- **Прочтение — указатели, а не строка на каждое сообщение.** У участника хранятся `last_read_message_id` и `last_delivered_message_id`; статус сообщения «отправлено / доставлено / прочитано» и счётчики непрочитанного вычисляются из них. ТЗ §20 называет сущность `MessageRead` — её роль выполняют эти два указателя: одна запись на участника чата вместо записи на каждую пару «сообщение × читатель».
- **Пересылка — ссылкой на оригинал.** Текст не копируется: пересланное сообщение указывает на исходное, и содержимое показывается только тому, кто вправе читать исходный чат. Остальные видят «пересланное сообщение недоступно». Переслать можно только то, что видишь сам.
- **Удаление — с пометкой.** Текст и вложения убираются, строка остаётся; удаление своего сообщения в журнал не пишется, удаление чужого модератором — пишется. Отложенное сообщение, ещё не отправленное, удаляется полностью.
- **Отложенная отправка.** `messaging:tick` раз в минуту отправляет наступившие; сообщение пересоздаётся с новым номером, чтобы встать в ленту по времени отправки, а не написания. До отправки его видит только автор.
- **Черновик** — поле у участника чата, одно на чат.
- **Ссылки-приглашения** — в базе только хеш токена; срок и число использований.
- **Задача из ветки** — создаётся обычным действием модуля Tasks; в описание попадает выжимка ветки, к корню ветки привязывается задача.
- **Поиск** — `LIKE` по тексту внутри доступных чатов. Полнотекстовый индекс — через общий `SearchService` (ТЗ §39), когда он появится; интерфейс `ChatReader::search()` при этом не изменится.

**Содержимое сообщений в журнал не пишется.** В журнале — создание чатов, состав, роли, ссылки, удаление чужих сообщений, заражённые вложения, изменения правил и срока хранения, чтение для расследования.

**Хранение (Д-27).** Бессрочно; срок в месяцах задаётся настройкой `messaging.retention_months`. `messaging:purge` (ежедневно) удаляет сообщения старше срока, каждая партия — запись в журнале.

## 3. Real-time: Laravel Reverb

Выбран **Laravel Reverb** (назван в ТЗ §20): собственный WebSocket-сервер на PHP, без внешнего сервиса; отдельный контейнер `reverb`.

- **По каналу идёт только сигнал «что-то изменилось»** (`ChatUpdated`: номер чата, вид изменения). Текст, автор, вложения не транслируются: страница, получив сигнал, перечитывает данные через сервер, где работает `ChatAccess`. Ошибка в авторизации канала не раскрывает содержимое.
- Каналы приватные: `chat.{id}` — тем, кто вправе читать чат; `messenger.{userId}` и канал панели — только владельцу.
- **Запасной путь** — опрос раз в 20 секунд: мессенджер работает и без WebSocket (`BROADCAST_CONNECTION=log`), только медленнее.
- Уведомления о сообщениях идут через центр уведомлений (категории «сообщения» и «упоминания»): одно непрочитанное уведомление на чат, уровень на чат — всё / только упоминания / без уведомлений.

**Цена пакета.** `laravel/reverb` 1.x несовместим с Guzzle 8 и PSR-7 3: установка понизила `guzzlehttp/guzzle` 8.2 → 7.15, `guzzlehttp/psr7` 3.1 → 2.13, `guzzlehttp/promises` 3 → 2.5. Guzzle 7 поддерживается; вернуться на 8 можно, когда Reverb его разрешит.

## 4. Антивирусная проверка вложений (T2)

ФО §6.6.4 требует проверку «на уровне инфраструктуры»; сервиса для неё в перечне ТЗ §59 нет.

- **Порт** `Files\AttachmentScanner` с вердиктами «чисто / заражено / проверка не выполнялась / сервис недоступен». Адаптеры: `ClamAvScanner` и `NullScanner`. Выбор — `ATTACHMENT_SCANNER=none|clamav`.
- **ClamAV** — демон `clamd` в отдельном контейнере (профиль `antivirus` в `docker-compose.yml`); файл передаётся потоком по TCP (`INSTREAM`), доступ демона к диску приложения не нужен. Сторонних PHP-пакетов нет. Адаптер проверен на настоящем демоне: чистый файл — «чисто», тестовая сигнатура EICAR — «заражено».
- **Вложения сообщений** проверяет задача очереди `ScanMessageAttachment`: до вердикта файл не отдаётся («проверяется»); заражённый удаляется с диска, в сообщении остаётся пометка, событие — в журнале.
- **Файлы постов и мероприятий** проверяются при загрузке через `Files\FileGate`: заражённый файл отклоняется сразу.
- **Демон недоступен — файл не считается чистым.** Пост или мероприятие файл не принимают; вложение сообщения остаётся «проверяется», проверка повторяется раз в минуту (до 10 попыток). При `ATTACHMENT_SCANNER=none` файлы помечаются «проверка не выполнялась» — режим локальной разработки и тестов.

**Для продакшена:** `ATTACHMENT_SCANNER=clamav` и работающий контейнер `clamav` (около 1,5 ГБ памяти под базы сигнатур).

## 5. Отклонения от ФО

| Что | Как сделано | Почему |
|---|---|---|
| Голосовые сообщения | Загрузка аудиофайла и проигрыватель в чате; записи с микрофона в браузере нет | Запись — отдельный клиентский компонент; уместна вместе с мобильным клиентом |
| Полнотекстовый поиск | `LIKE` по доступным чатам | Общий поиск (ТЗ §39) ещё не построен |
| Индикатор «печатает» | Нет | В ФО §6.6 не требуется |
| `MessageRead` | Указатели прочтения у участника | См. §2 |

## 6. Последствия

- Новое место, показывающее сообщения, начинает с `ChatAccess` / `ChatReader`; собственные запросы к `messages` запрещены так же, как к `posts` и `events`.
- Новый тип объекта с обсуждением регистрирует правило в `ChatSubjects` в своём сервис-провайдере.
- Новые места загрузки файлов вызывают `FileGate::ensureAcceptable()`.
- В продакшене нужны два дополнительных процесса: `reverb` и `clamav`.
