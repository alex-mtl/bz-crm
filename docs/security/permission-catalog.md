## 1. Модель доступа: код ∩ слой данных

Доступ **не бинарный**. Каждое действие над объектом проверяется одним сервисом `AuthorizationService` (ТЗ §15) как пересечение четырёх условий:

```
разрешено =  код разрешения есть у одной из действующих ролей пользователя
          ∧  объект попадает в область действия этой роли (или связь даёт доступ — «Св»)
          ∧  правила самого объекта это допускают (слой данных)
          ∧  для полей — права на поле ∧ выбор владельца (Д-13)
          ∧  нет явного запрета (deny перекрывает allow)
```

Кроме того, есть **жёсткие ограничения** — они действуют поверх ролей, и никакая роль их не отменяет:
- тот, о ком заметка «360», её не видит (Д-14);
- заявитель на рассмотрении не получает внутренних данных (ФО §6.1);
- автоматика и AI действуют только через те же проверки (ТЗ §45);
- счётчики и агрегаты не раскрывают недоступные объекты (ТЗ §67).

**Пример.** У сотрудника есть код `chats.read` (да). Слой данных: «только чаты, где он участник». Значит, он читает свои чаты и не видит чужие, в том числе в поиске и счётчиках. Читать чаты без участия — отдельный зарезервированный код `chats.read.investigation`, по умолчанию его нет ни у кого.

**Области действия** (назначаются вместе с ролью):

| Обозн. | Область |
|---|---|
| О | вся организация |
| Т | свои территории: поддерево, по правилам Д-3 |
| П | своё подразделение и дочерние |
| С | только свои объекты (автор, владелец, сам человек) |
| Св | по связи: начальник (Д-11), участник чата, группы, проекта, исполнитель и т.п. — вычисляется политикой, не назначается |

**Роли по умолчанию.** Стартовая раздача, суперадмин меняет её в конструкторе без правки кода (ФО §3.5). Сокращения:

| Сокр. | Роль | Источник |
|---|---|---|
| СА | Суперадмин | ФО §4.1 |
| РО | Руководитель организации | ФО §4.1 |
| РП | Руководитель подразделения / региона | ФО §4.1 |
| Сотр | Сотрудник / активист | ФО §4.1 |
| Вол | Волонтёр | ФО §4.1 |
| Канд | Кандидат (внешний участник с учётной записью) | ФО §4.1 |
| HR | HR | ФО §4.1 |
| СБ | Служба безопасности | ФО §4.1 |
| Псих | Психолог / наблюдатель | ФО §4.1 |
| АдмС | Администратор справочников | добавлена, Д-16 / Д-17 |
| Опер | Оператор входящих | добавлена, Д-17 (ФО §5.5) |
| Мод | Модератор (глобальный или региональный — через область действия) | добавлена, Д-17 (ФО §6.4.4) |

«Непосредственный начальник» и роли внутри групп и чатов (владелец, админ, модератор группы) — это **связи** (область «Св»), а не назначаемые роли. «Гость» — без учётной записи, работает через публичный API (ТЗ §47).

**Зарезервированные коды** (помечены 🔒) — существуют в каталоге, но по умолчанию не выданы никому; выдаются только явно. Для них действует исключение из автотеста полноты с обратной проверкой (принято, Д-17).

| `appeals.export` | экспорт обращений | О, Т, П | СА, РО |
| `segments.read` | сегменты и сохранённые фильтры организации | О, Т, П — состав сегмента фильтруется по области читающего | СА, РО, HR (О); РП (Т, П); Опер (Т) |
| `segments.manage` | создание общих сегментов | О, Т, П | СА, РО, HR (О); РП (Т, П) |
| `crm.import` | импорт людей, лидов, обращений с предпросмотром и dry-run | О | СА, HR |

> Уточнения фазы 3:
> - **HR** получает `pipelines.read`, `pipelines.write`, `leads.close`, `appeals.read`, `appeals.create`, `appeals.close` **по связи** (как ответственный) — так же, как сотрудник. Причина: HR приглашает сотрудников, а выдать можно только то, что есть у самого (Д-17); ФО §4.1 даёт HR доступ к воронке кандидатов.
> - `appeals.create` для сотрудника — «Св»: обращение своей территории (с учётом выданных территорий) или своего подразделения.
> - `appeals.close` означает работу со статусом обращения: взять в работу, выполнить, отклонить, создать задачу. Вернуть закрытое обращение в работу может только тот, у кого есть `appeals.assign`.
> - `crm.import` нужен вместе с `people.import`, когда при импорте людей сразу создаются лиды; сами лиды требуют ещё и `leads.create`.
> - `segments.manage` позволяет менять чужой общий сегмент, только если его автор находится в области этого права; личный фильтр доступен каждому, кто читает людей.

**Реализация (фаза 4, [ADR-010](../decisions/ADR-010-social-visibility-groups-api.md)).**
- `posts.read` — не область роли, а видимость каждого поста (`PostVisibility`). Публичные посты видят все с учётной записью, включая кандидатов и волонтёров (Д-25). Сверх публичного кандидат видит только «явно открытое»: посты групп, куда его пригласили, и посты, адресованные ему лично; региональные — нет. Суперадмин чужие приватные посты и посты секретных групп не видит.
- `posts.publish.region` выдан также HR в том же слое, что и сотруднику («Т — свои территории»): HR приглашает сотрудников и по правилу «не больше, чем у себя» должен иметь то, что выдаёт. «Целевой список из роли» требует `posts.publish.global`.
- `posts.pin`: глобально — держатель права на всю организацию; в территории — в области роли или в пределах собственного территориального доступа; в группе — владелец и админ группы (по связи, без системного права).
- `moderation.*` определяются по **автору** контента (`PersonLocator`): руководитель подразделения достаёт посты и комментарии своих сотрудников. Модератор группы получает `moderation.queue.read`, `moderation.hide`, `moderation.revisions.read` на контент своей группы по связи. Автор поста может скрывать комментарии под своим постом (ФО §6.4.3). Предупреждение и мут — только СА и Мод.
- `groups.manage`, `groups.moderate` — роль внутри группы; у суперадмина — как системное право на видимые ему группы. `groups.link.manage` покрывает также привязку к территории.

**Реализация (фаза 5, [ADR-011](../decisions/ADR-011-events-and-notifications.md)).**
- `events.read` — видимость мероприятия (`EventVisibility`); приглашённый видит мероприятие при любом уровне. Мероприятия «для всей организации» видят все с учётной записью (Д-25); сверх этого кандидат видит только то, куда приглашён. Держатель `events.update` по роли видит все мероприятия, организаторы которых — в области этой роли (Д-24): руководитель — мероприятия подчинённых, суперадмин — все.
- `events.create`: у сотрудника и HR право выдано в слое «свои» — закрытые мероприятия и мероприятия своих групп; региональное мероприятие требует права без этого сужения и территории в пределах области роли или собственного территориального доступа; «для всей организации» — права на всю организацию. Админ группы проводит мероприятие группы по связи.
- `events.update`, `events.invite`, `events.attendance.mark`, `events.results.publish` — организатор по связи; по роли — в области, где работает организатор (эта же область даёт и видимость, Д-24). Приглашать можно людей, которых приглашающий видит (`people.read`); `events.invite.bulk` ограничивает массовое приглашение областью права и активными учётными записями.
- `notifications.broadcast` — получатели только в области роли; `notifications.critical.send` — всем получателям по всем каналам, с подтверждением прочтения. Шаблоны писем в `notifications.defaults.manage` пока не редактируются (фаза 9–10).

## 15. Правила каталога

1. Новый модуль регистрирует свои коды в каталоге вместе со слоем данных и тестами «может / не может» на демо-мире (Д-2). Это часть Definition of Done.
1a. **Суперадмин получает каждый незарезервированный код автоматически** при появлении кода. Иначе правило «не больше, чем у себя» не дало бы ему управлять ролями, в которых есть этот код (найдено тестом в фазе 1). В таблицах выше СА указан там, где он есть и по смыслу; автоматическая выдача гарантирует остальное.
2. Автотест: у каждого кода явно указана хотя бы одна роль по умолчанию, **кроме зарезервированных 🔒**; для 🔒 — обратная проверка: по умолчанию не выдан никому; у каждого 🔒 есть обоснование; явная выдача 🔒 пишется в журнал (принято, Д-17).
3. У каждого кода есть описание на ro/ru/en.
4. Правило «не больше, чем у себя» (принято, Д-17): `roles.assign`, `delegations.manage`, `users.invite` не могут выдать права или область шире собственных; попытка отклоняется и пишется в журнал.
