# BZ-CRM-Social — инструкции для Claude Code

## Источники истины
- `docs/functional-spec.md` — ЧТО делает система; `docs/technical-architecture-v1.md` — КАК; `docs/requirements-addendum.md` — более поздние решения заказчика, имеют приоритет над исходниками. При конфликте — ТЗ §0: не упрощать и не переосмысливать функциональность молча; неоднозначность — остановиться и спросить.
- Новое решение заказчика, меняющее требования, — записывать в `docs/requirements-addendum.md` (Д-N), а не править исходные документы.
- План фаз — `IMPLEMENTATION-PLAN.md`. Текущее состояние архитектуры — `docs/architecture.md`, решения — `docs/decisions/`, открытые вопросы — `docs/open-questions.md`.
- Работать строго по фазам. Следующую фазу начинать только по явной команде пользователя (ТЗ §86). В конце фазы — отчёт: сделано / тесты / решения / открытые вопросы / риски / следующая фаза.

## Окружение — только Docker
На хосте (Windows) нет PHP, Composer, MySQL, Redis. Не устанавливать их на хост. Всё — через контейнеры:

```bash
docker compose up -d
docker compose exec app php artisan <команда>
docker compose exec app composer <команда>
docker compose exec app composer check        # Pint + Larastan + Pest — перед завершением любой задачи
docker compose exec node npm run build
```

- В Git Bash при абсолютных Linux-путях в аргументах — `export MSYS_NO_PATHCONV=1`.
- `vendor/`, `node_modules/`, `storage/framework/` — на именованных томах Docker (ADR-004). Папка `vendor/` на хосте устаревшая и контейнерами не используется: при чтении исходников пакетов учитывать это или смотреть в контейнере.
- Порты: приложение 8100, Mailpit 8126, Vite 5174, MySQL 3316, Reverb (WebSocket) 8180. Тестовая БД — `bz_crm_testing` (MySQL, не SQLite).

## Обязательные правила (ТЗ)
- Бизнес-логика — только в `app/Domain/<Module>` (Actions/Services/Queries). Filament, Livewire, контроллеры — тонкий слой (ТЗ §8, §61–63).
- Любая проверка прав — через единый сервис авторизации (ТЗ §15, §64). Скрытие кнопки — не проверка.
- `User` ≠ `Person`; всё, что касается человека, ссылается на `person_id` (ТЗ §12).
- Строки интерфейса — только через `lang/` (ro по умолчанию, ru, en). Коды статусов в БД — английские (ТЗ §48).
- Схема — только миграциями; без БД-специфичного SQL и нативных ENUM (ТЗ §5, §79, §81).
- Новый внешний пакет — только после оценки по ТЗ §70 и, при архитектурной значимости, с ADR.
- Definition of Done — ТЗ §76, расширенный Д-2; тесты доступа по матрице ТЗ §52 для каждого чувствительного модуля.
- «Регион / район / сектор» — это `Territory`, не подразделение (Д-1). Подразделение и сотрудник привязываются к 0..N территориям; сотрудник наследует территории подразделений, дополнительные выдаёт руководитель или вышестоящий с правом (Д-3).
- Доступ — «код ∩ область ∩ слой данных ∩ поля, deny перекрывает» (Д-17, ADR-003). Каталог кодов со слоем данных — `docs/security/permission-catalog.md`; новый модуль регистрирует там свои коды и покрывает их тестами «может / не может».
- Почти все перечни (типы, статусы, приоритеты, причины) — справочники, а не жёсткие списки (Д-16). Стартовые справочные данные — `database/data/` (загружаются во всех окружениях, в отличие от демо-мира).
- Журнал событий (Д-4, ADR-006): любое значимое действие, включая назначение прав, пишет запись через API модуля `Audit` в той же транзакции. Действие без записи в журнале не считается реализованным. Новые типы событий регистрируются в каталоге с описаниями на ro/ru/en.

## Демо-мир (Д-2) — обязателен в каждой фазе
- Любая новая возможность сразу получает демо-данные в едином вымышленном мире (`Database\Seeders\Demo\*`): пример «разрешено» и пример «запрещено», все статусы и граничные случаи. Новые данные достраивают существующий мир теми же персонажами, а не создают параллельный.
- Демо-данные создаются через доменные Actions, а не прямыми вставками; только вымышленные люди, домен `demo.bz-crm.test`, общий пароль из `DEMO_USER_PASSWORD`; даты относительно «сейчас»; детерминированно; в `production` запуск запрещён.
- Каждое «может / не может» подтверждается сценарным тестом в `tests/Scenarios` и описано в `docs/demo/README.md` со ссылкой на тест.
- Фаза не закрыта, пока `migrate:fresh --seed` не поднимает полный демо-мир и сценарные тесты не зелёные.

## Известные особенности
- Произвольные Tailwind-классы в шаблонах Filament работают только через тему `resources/css/filament/admin/theme.css` (ADR-005) — после изменений нужен запущенный `node` или `npm run build`.
- Тесты вызывают `withoutVite()` (`tests/TestCase.php`) и не зависят от собранных ассетов.
- Замыкания, отправленные в очередь из `tinker`, воркер не может десериализовать — для проверки очереди использовать настоящие классы задач.
- Шаблоны, подключаемые в Filament через render hooks (`resources/views/auth/*`), тоже должны быть в `@source` темы.
- Сценарные тесты (`tests/Scenarios`) работают в отдельной БД `bz_crm_scenarios` (создаётся `docker/mysql/init/02-scenarios-db.sql`; на существующем томе — выполнить этот SQL вручную). Мир сидится один раз на тестовый класс, тест — в транзакции с откатом.
- В тестах при смене пользователя в одной сессии вызывать `$this->flushSession()`: `AuthenticateSession` Filament сравнивает хеш пароля предыдущего пользователя.
- Filament-ресурсы: `$hasTitleCaseModelLabel = false` (Title Case неправилен для ro/ru); видимость — через `App\Filament\Concerns\ChecksPermissions`, выполнение — только через доменные Actions.
- Демо-сидер не повторяется на заполненной базе — пересборка мира: `migrate:fresh --seed`.
- Замыкания Filament получают аргументы **по имени** (`$query`, `$search`, `$data`, `$value`, `$record`…). Параметр с другим именем (`$q`, `$s`) молча получает пустой объект из контейнера — список падает или фильтр не работает.
- Списки в панели фильтруются только через `ChecksPermissions::scoped($query, '<код>')` → `AuthorizationService::scopeQuery` (область ∩ слой данных в SQL, ADR-008). Новый модуль регистрирует для своих моделей `ScopeLocator` и отношения «Св» в своём сервис-провайдере.
- Системные настройки кешируются в Redis; после `migrate:fresh` кеш сбрасывается слушателем `MigrationsEnded` (`SystemSettings::flush()`) — без этого сидеры видят устаревшие значения.
- Новый модуль с колонкой, указывающей на человека (`person_id` и т.п.), регистрирует её в `People\PersonReferences` в своём сервис-провайдере — иначе при слиянии карточек (ADR-009) его данные останутся у архивного дубля. Одна строка на человека или значения по другому ключу — через `registerHandler`.
- Человек вне оргструктуры «живёт» в территории карточки и в ответственном подразделении (`PersonLocator`, ADR-009). Лиды, обращения, задачи хранят свои `org_unit_id` / `territory_id` и проверяются `UnitColumnLocator`.
- CSV и XLSX читаются и пишутся только через `App\Support\Spreadsheet\Spreadsheet` (OpenSpout, ADR-009). Файлы импорта и экспорта — на диске `local`; в тестах — `Storage::fake('local')`.
- В `DemoSteps` вложенный `at()` по завершении возвращает часы к «сейчас», а не ко времени внешнего шага: всё, что должно произойти во время шага, писать до вложенных `at()`.
- Конструктор ролей (`SetRolePermissions`) сохраняет слой данных оставшихся прав; новому праву даёт слой из стартовой раздачи. Права на группы полей меняет только `SetFieldGroupRights`.
- Всё, что показывает посты, начинает с `Social\PostVisibility::visibleTo()` (лента — `Social\Feed`), всё, что показывает группы, — с `Groups\GroupAccess::visible()` (ADR-010). Собственные запросы к `posts` / `groups` в экранах, API, отчётах, уведомлениях запрещены: иначе утечёт невидимый пост или секретная группа. Комментарии, реакции, вложения проверяются через пост.
- Модерация определяется по автору контента (`PersonLocator` по `author_person_id`) и по роли в группе (отношение `RELATION_GRANT`); роль внутри группы — не системная роль. Мут действует по часам (`expires_at`), `social:tick` только закрывает истёкшие и публикует отложенные посты.
- API v1 — `routes/api.php` (подключён в `bootstrap/app.php`: `web`, `auth`, троттлинг). Контроллеры API не содержат правил — только вызывают доменные сервисы; невидимый объект отвечает 404.
- Всё, что показывает мероприятия, начинает с `Events\EventVisibility::visibleTo()` (ADR-011); управление мероприятием — только через `EventVisibility::authorizeManaging()` (право **и** видимость). Руководитель видит мероприятия людей своей области при любом уровне видимости, суперадмин — все (Д-24); на ленту и секретные группы это не распространяется.
- Новое уведомление: класс с трейтом `Notifications\Concerns\RoutesByPreference`, методом `category()` и `toDatabase()`; свои `via()` и `toMail()` не писать. Категорию регистрирует модуль в `NotificationCategories`. Если уведомление о предмете с ограниченной видимостью — в нагрузке `'subject' => ['<код>', id]`, метод `shouldSend()` с проверкой видимости, и вызов `Notifications\Retraction` там, где доступ к предмету отнимается (ТЗ §37).
- Работа планировщика, которая что-то рассылает (напоминания, дайджесты), обязана быть идемпотентной: сначала «захват» строки (`UPDATE … WHERE sent_at IS NULL` или уникальный ключ периода), потом отправка.
- Демо-сидер на время сидирования переключает очередь в `sync` и почту в `array`: уведомления получают дату демо-шага, письма наружу не уходят.
- Ключи в файлах `lang/` — только строковые: числовые ключи вложенных массивов помощник слияния превращает в список.
- Тесты, которые двигают время (`travel`), задают исходные моменты относительно `now()` без `setTime()`: иначе результат зависит от времени суток запуска.
- Правки существующих файлов — инструментом Edit или скриптом со строгой проверкой числа замен **до** записи. Скрипт с `preg_replace` без проверки результата однажды обнулил `routes/web.php`.
- Всё, что показывает чаты и сообщения, начинает с `Messaging\ChatAccess` / `ChatReader` (ADR-012): диалог и групповой чат читают только участники — никакая роль чат не открывает; обсуждение объекта читает тот, кто читает объект. Новый тип объекта с обсуждением регистрирует правило в `Messaging\ChatSubjects`. Содержимое сообщений в журнал и в WebSocket-события не попадает.
- Новое место загрузки файлов вызывает `Files\FileGate::ensureAcceptable()`; вложения сообщений проверяет задача очереди. В тестах и локально сканер выключен (`ATTACHMENT_SCANNER=none`); ClamAV — `docker compose --profile antivirus up -d clamav`.
- Real-time — контейнер `reverb` (порт 8180). В тестах вещание выключено (`BROADCAST_CONNECTION` из `phpunit.xml`); страница, слушающая канал, обязана иметь запасной `wire:poll`.
- Даты в демо-сидерах — через `DemoSteps` (`at()`, `as()`); сроки задач, которые должны быть «просрочены сейчас», — относительно реального «сейчас» (`dueIn`), а не шага сидера.
