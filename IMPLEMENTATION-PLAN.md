## Принципы, действующие во всех фазах

- Каждая фаза закрывается по Definition of Done ТЗ §76, **расширенному Д-2 и Д-4**: БД → модель → валидация → авторизация → бизнес-логика → UI → API (где нужно) → **запись в журнал событий** → доменные события → уведомления (где нужно) → тесты → переводы (ro/ru/en) → документация → **демо-данные → сценарные тесты на демо-данных → обновлённый `docs/demo/README.md`**.
- Каждый новый модуль регистрирует свои коды разрешений со слоем данных (Д-17) и свои справочники (Д-16); без этого модуль не считается готовым.
- Журнал событий (Д-4) существует с первого блока фазы 1. Любое значимое действие в любом модуле, включая назначение прав, пишет в него запись в той же транзакции. Действие без записи в журнале не считается реализованным.
- Порядок работы внутри фазы — ТЗ §77. Следующая фаза не начинается, пока тесты текущей не зелёные и `migrate:fresh --seed` не поднимает полный демо-мир без ошибок.
- Авторизация одна на всех: Web, Livewire, Filament, API, поиск, отчёты, экспорт, джобы, уведомления (ТЗ §15, §64).
- Бизнес-логика — в Actions/Services/Query-классах, не в Filament Resources и не в Blade (ТЗ §8, §61–63).
- Все изменения схемы — только через миграции, без БД-специфичного SQL вне изолированных классов (ТЗ §5, §79, §81).
- После каждой фазы — отчёт: что сделано, тесты, решения (ADR), открытые вопросы, риски, следующая фаза (ТЗ §86).

## Демо-мир — сквозное требование (Д-2)

Параллельно с кодом в каждой фазе растёт **один связный вымышленный мир** — организация с территориями, подразделениями, людьми и их деятельностью. На нём видно всё, что система умеет, и всё, что она запрещает. Подробные правила — в [Д-2](docs/requirements-addendum.md#д-2-демо-наполнение-платформы-параллельно-с-разработкой). Кратко:

- данные создаются через доменные Actions, поэтому проходят ту же валидацию, права, аудит и события, что и реальные действия;
- для каждой возможности есть пример «разрешено» и пример «запрещено»;
- представлены все статусы и граничные случаи;
- только вымышленные люди, email на домене `demo.bz-crm.test`, общий пароль демо-учёток из `.env`;
- детерминированно; даты относительно момента генерации;
- запуск в `production` заблокирован кодом и тестом;
- сценарные тесты (`tests/Scenarios`) проверяют утверждения «персонаж X может / не может Y» на самом демо-мире; `docs/demo/README.md` описывает персонажей и сценарии демонстрации и ссылается на эти тесты;
- отдельный объёмный профиль (тысячи людей, десятки тысяч задач и сообщений) — для нагрузочных тестов (ФО §3.4, ТЗ §53).

Конкретные имена и детали фиксируются в `docs/demo/README.md` при реализации. Каркас, который закладывается в фазах 1–2 и дальше только дополняется:

- в «Chișinău» — секторы «Centru» и «Botanica» для двух зеркальных филиалов (секторы — из Закона 764/2001);
- «Bălți» (макрорегион Север) и «Cahul» (Юг) — оба покрыты «Администрацией Север–Юг», «Bălți» также своей региональной организацией;
- «Ungheni» — регион без подразделения (территория без структуры);
- руководитель организации — с доступом ко всему узлу «Молдова» одним назначением (Д-7);
- остальные единицы — пустые, но присутствуют: видно, что справочник полный.

**Подразделения** — без территорий, с одной и с несколькими (Д-1, Д-3):
- «Центральный аппарат» — без территорий, внутри: HR, Коммуникации, Служба безопасности;
- «Администрация Север–Юг» — привязана сразу к двум регионам, «Bălți» и «Cahul»;
- «Региональная организация Chișinău» — привязана к региону «Chișinău», внутри два филиала, каждый привязан к своему району;
- «Региональная организация Bălți» — привязана к региону «Bălți».

## Зависимости между фазами, которые нужно заложить заранее

0. **Журнал событий — самым первым (Д-4).** Всё, что делается после него, сразу пишет в журнал. Поэтому он — блок 1.0 фазы 1, раньше демо-инфраструктуры, входа и регистрации: демо-мир тоже создаётся через Actions и наполняет журнал реальной историей.
1. **Минимальная модель чата — в фазе 2.** ФО требует, чтобы у задачи сразу был чат обсуждения (§6.8.2), а у группы — свой чат (§6.5). Задачи и группы идут раньше мессенджера, поэтому в фазе 2 закладывается минимальная модель `Chat` / `ChatMember` / `Message`: одна ветка на задачу, без тредов, реакций и real-time. В фазе 6 она не пишется заново, а достраивается (ТЗ §21, §64).
2. **Базовые территории — в фазе 2 (Д-1).** Область прав «регион» и видимость постов «региональный» строятся по `Territory`. Поэтому иерархия Страна → … → Избирательный участок появляется вместе с оргструктурой в фазе 2. Фаза «Гео» добавляет к ней дома, квартиры, обходы, геозоны, карты и офлайн.

## Фаза 1 — Ядро: журнал событий, аутентификация, регистрация, базовый доступ ✅ выполнена

**Итог (2026-09-30):** все блоки 1.0–1.4 реализованы; `migrate:fresh --seed` поднимает демо-мир фазы 1; `composer check` зелёный (Pint, Larastan, Pest: Unit / Feature / Scenarios / Architecture). Состояние модулей — [`docs/architecture.md`](docs/architecture.md) §4, персонажи и сценарии — [`docs/demo/README.md`](docs/demo/README.md), уточнения решений — ADR-003, ADR-006, ADR-007.

Отклонения от плана ниже:
- «Не больше, чем у себя» проверено на коде `users.approve` (роль HR), а не `people.export`: этот код появляется вместе с CRM в фазе 3, тогда сценарий дополняется.
- E2E-сценарии («вход», «инвайт», «самостоятельная регистрация → заявка → решение», «вход через Google/Facebook», «2FA», «сброс пароля») — HTTP/Livewire-тесты Pest на уровне страниц и действий; браузерные E2E (Dusk/Playwright) не подключались — это отдельное решение по ТЗ §70, вынесено в открытые вопросы.
- OAuth проверен на фиктивном шлюзе (`tests/Support/FakeOAuthGateway`); реальные Google/Facebook требуют client ID/secret заказчика — провайдеры созданы выключенными.

**Цель:** сначала гибкий журнал событий (Д-4), на который опираются все последующие функции; затем вход и регистрация, включая сторонних провайдеров, и базовая ролевая модель.

### 1.0. Журнал событий (Д-4, ADR-006) — первый блок
- В начале блока — решение T6: собственный модуль `Audit` или `spatie/laravel-activitylog` как хранилище. Предварительно — собственный модуль, обоснование в ADR-006.
- Единое API записи для всех модулей: `EventJournal::record(...)` и слушатель доменных событий. Модули не пишут в таблицу журнала напрямую.
- Каталог типов событий: код, категория, важность, правила маскировки, описания на ro/ru/en. Каждый модуль регистрирует свои типы. Незарегистрированный тип — ошибка.
- Полный контекст записи:
  - кто: пользователь, человек, система, задача очереди, автоматизация, AI;
  - под чьими правами: собственные, делегирование, имперсонация;
  - над чем, старые и новые значения (секреты и чувствительные поля маскируются);
  - IP, устройство, `request_id`, `correlation_id`.
- Контекст собирается автоматически: middleware для HTTP; передача в задачи очереди, чтобы фоновые действия сохраняли корреляцию; пометка консольных команд и сидеров.
- Запись — в той же транзакции, что и действие. Откат действия откатывает запись; действия без записи не бывает.
- Неизменяемость: запрет изменения и удаления в приложении плюс механизм на уровне БД (выбор в ADR-006). Сроки хранения по категориям настраивает суперадмин. Очистка по сроку — только отдельной командой под отдельной привилегией, и сама очистка логируется.
- Интерфейс в Filament: фильтры по актору, типу, категории, объекту, периоду, корреляции; история объекта; история действий человека. Доступ по привилегии `audit.read`, экспорт — по отдельной. Просмотр и экспорт журнала тоже логируются. В фазе 2 просмотр получает области действия (например, руководитель региона — только события своего региона).
- Типы событий фазы 1 регистрируются сразу: вход, выход, неудачный вход, регистрация, решение по заявке, изменение ролей и прав, изменение настроек провайдеров входа, демо-вход, просмотр и экспорт журнала.

### 1.1. Инфраструктура демо-мира (Д-2, Д-5)

- Защита от запуска в `production` + тест на эту защиту.
- Фиксированный seed генератора, общий пароль `DEMO_USER_PASSWORD` из `.env`, относительные даты.
- Демо-данные создаются через Actions, поэтому журнал с первого запуска содержит осмысленную историю мира. Записи сидера помечены как системные с отдельной корреляцией.
- Набор `tests/Scenarios` (загружает демо-мир один раз на прогон, каждый тест — в транзакции) + группа в `phpunit.xml`.
- `docs/demo/README.md` — таблица персонажей, сценарии демонстрации, ссылки на тесты.
- Каркас объёмного профиля (генератор большого набора для нагрузочных тестов); наполнение — по мере появления модулей.
- **Быстрый вход под персонажами (Д-5):** в окружениях `local`/`demo` на странице входа — список демо-персонажей. В `production` блок не регистрируется вовсе. Быстрый вход — обычный вход под учёткой персонажа (не имперсонация), в журнале помечается как «демо-вход».

### 1.2. Функциональность
- Разделение `User` (учётная запись) и `Person` (человек), связь 1:0..1 — с первой миграции (ТЗ §12, ФО §7).
- Вход по email/паролю, подтверждение email, сброс пароля, активация/деактивация без удаления данных (ФО §6.1, ТЗ §13).
- **OAuth/OIDC:** Google и Facebook как стартовый набор, за абстракцией провайдеров. Реестр провайдеров расширяется суперадмином через интерфейс без правки кода. Client secret хранится зашифрованным, в UI — только факт наличия. Несколько способов входа на один аккаунт (ФО §6.1, ТЗ §13).
- Три пути регистрации (ФО §6.1):
  1. по приглашению — основной;
  2. самостоятельная (провайдер или email) → нулевые права, статус «заявка на рассмотрении», лендинг со статусом;
  3. публичная форма → **кандидат** (`Person` без `User`). Сама сущность закладывается здесь, реальный приём из форм — в фазе 10.
- Рассмотрение заявок по праву `users.approve`: одобрить с назначением ролей или отклонить с причиной, видимой заявителю.
- **Возможные дубли при самостоятельной регистрации (Д-10):**
  - автоматической привязки к существующей карточке нет никогда — регистрация всегда создаёт новую карточку;
  - сервис поиска возможных совпадений (модуль People): email, нормализованный телефон, похожее ФИО — только подсказка с указанием признака совпадения;
  - на экране заявки рассматривающий видит подсказку «возможно, это уже существующий человек»;
  - ручная привязка по отдельному праву `users.link_accounts`: способ входа присоединяется к существующему аккаунту, лишняя учётная запись деактивируется, лишняя карточка помечается как дубль, история сохраняется;
  - подсказку можно отклонить («это разные люди»); привязка, отмена и отклонение пишутся в журнал.
- TOTP 2FA, журнал входов, принудительное завершение всех сессий, rate limiting, защита от перебора (ФО §3.1, §6.1; ТЗ §13).
- Базовая ролевая модель `Role` / `Permission` / `UserRole`, стартовый набор системных ролей (ФО §4.1) плюс «Администратор справочников», «Оператор входящих», «Модератор» (Д-17), конструктор ролей в Filament. Scopes — в фазе 2.
- **Каталог разрешений (Д-17):** коды фазы 1 из [`docs/security/permission-catalog.md`](docs/security/permission-catalog.md) регистрируются с описаниями ro/ru/en; автотест полноты с исключением зарезервированных кодов.
- Центральный сервис авторизации `AuthorizationService` создаётся здесь (ТЗ §15, ADR-003) сразу по модели «код ∩ область ∩ слой данных ∩ поля, deny перекрывает» (Д-17). В фазе 1 из слоёв работают код, «свои объекты» и жёсткие ограничения; области по территориям и оргструктуре подключаются в фазе 2 без переделки сервиса.
- **Справочники (Д-16):** единый механизм справочников: коды, названия ro/ru/en (при создании автоматически копируются из языка ввода в два других с пометкой «перевод не проверен» — без блокировки), системные элементы, деактивация вместо удаления, слияние дублей; очередь предложений с одобрением администратором справочников и проверкой на дубли (правила приняты, Д-16); все изменения — в журнал. Сюда же загружаются стартовые справочные данные из `database/data/catalogs/`.
- Каждое действие этого блока пишет событие в журнал (1.0).

### 1.3. Демо-данные
- Все персонажи из каркаса демо-мира как `Person` + `User` с базовыми ролями. К подразделениям и территориям их привязывает фаза 2.
- Кандидат без учётной записи; заявки в статусах «на рассмотрении» и «отклонена» с причиной; деактивированный пользователь.
- Пользователь со связанным Google-аккаунтом (фиктивный идентификатор провайдера); пользователь с включённой 2FA.
- Возможные дубли (Д-10): сотрудник филиала A, приглашённый ранее, и его же заявка через Google с тем же email — висит с подсказкой; уже выполненная ручная привязка другой пары (два способа входа на одном аккаунте); отклонённая подсказка по однофамильцам — два разных человека с одинаковым ФИО.
- Входы: успешные и неуспешные, в том числе серия неудачных попыток.
- Отправленное приглашение: использованное, активное и просроченное.
- Журнал событий содержит историю всех этих действий — с правильными акторами, корреляцией и замаскированными секретами.

### 1.4. Сценарные тесты
**Журнал событий:**
- Изменить или удалить запись журнала через приложение невозможно.
- Откат действия откатывает запись; каждое действие фазы оставляет запись нужного типа.
- Пароли, токены, client secret в журнале замаскированы.
- Пользователь без `audit.read` не видит журнал ни в интерфейсе, ни через API. Просмотр журнала сам попадает в журнал.
- Все записи одного действия (например, одобрение заявки с назначением ролей и отправкой письма через очередь) связаны одним `correlation_id`.
- Незарегистрированный тип события отклоняется; у каждого типа есть описания на ro/ru/en.

**Вход и регистрация:**
- Заявитель на рассмотрении при входе видит только лендинг со статусом и не получает внутренних данных ни через UI, ни через API.
- Отклонённый заявитель видит причину отказа.
- Деактивированный пользователь не может войти, его история сохранена.
- Пользователь без роли с правом администрирования не открывает конструктор ролей.
- «Не больше, чем у себя» (Д-17): пользователь без `people.export` не может назначить роль или делегировать права, содержащие `people.export`, и не может пригласить человека с такой ролью; попытка отклоняется и пишется в журнал.
- Зарезервированные права 🔒 (Д-17) не выданы никому по умолчанию; явная выдача суперадмином записана в журнал.
- Суперадмин одобряет заявку — в журнале появляется запись с выдавшим, получателем и назначенными ролями.
- Просроченное приглашение не срабатывает.

**Возможные дубли (Д-10):**
- Самостоятельная регистрация с email существующего сотрудника **не** привязывается к его карточке и не даёт доступа к его данным.
- Рассматривающий заявку видит подсказку о возможном совпадении с признаком совпадения.
- Без права `users.link_accounts` привязать нельзя.
- После ручной привязки сотрудник входит обоими способами в один аккаунт; лишняя карточка помечена как дубль, история сохранена; в журнале — запись с тем, кто привязал.
- Отклонённая подсказка по однофамильцам больше не показывается.
- Быстрый вход персонажей есть в `local`/`demo` и отсутствует в `production`.

**Готово, когда:** журнал событий работает и покрыт тестами; зелёные E2E-сценарии «вход», «инвайт», «самостоятельная регистрация → заявка → одобрение/отклонение», «вход через Google/Facebook», «2FA», «сброс пароля»; зелёные сценарные тесты 1.4.

Узел «Молдова» даёт доступ ко всей стране одним назначением.
- **Наполнение из официальных данных (Д-6, Д-8)** — файлы в [`database/data/geo/`](database/data/geo/README.md):

- **Непосредственный начальник (Д-11)** — хранимая связь «сотрудник → начальник»:
  - при создании карточки по умолчанию — руководитель подразделения;
  - руководитель подразделения может сменить начальника в карточке сотрудника; смена сразу переносит видимость служебного слоя, HR-характеристики и заметок «360», право выдавать территории, подсказки о втором аккаунте, эскалации задач; всё пишется в журнал и видно в истории карточки;

- Сотрудник так же может быть напрямую привязан к нескольким территориям (Д-3).

### 2b. Полноценная модель прав
- Права вида `модуль → объект → поле → действие` (ФО §6.2, ТЗ §14).
- Две независимые оси областей действия: по территории (регион / район / сектор) и по оргструктуре (подразделение), плюс «организация», «группа», «свои», «подчинённые».
- **Территориальный доступ сотрудника (Д-3):**
  - действующий доступ = территории его подразделения (наследуемый; подразделение одно — Д-11) ∪ его прямые назначения; каждая территория покрывает своё поддерево;
  - при переводе в другое подразделение или изменении территорий подразделения наследуемый доступ пересчитывается автоматически, прямые назначения сохраняются;
  - подразделение без территорий доступа по этой оси не даёт.
- **Выдача дополнительных территорий (Д-3):**
  - отдельное право (например, `access.territories.grant`); выдаёт непосредственный руководитель или вышестоящий сотрудник с этим правом;
  - назначение хранит, кто и когда выдал; отзыв возможен;
  - ограничения (Д-3, приняты): выдать можно только в пределах собственного действующего доступа; у назначения может быть срок окончания — по нему доступ отзывается автоматически планировщиком, с записью в журнале; причина при выдаче обязательна.
- Симулятор прав «глазами сотрудника» показывает не только что доступно, но и **откуда** это: «регион X — от подразделения Y», «район Z — выдан руководителем N до даты D».
- Временные роли и делегирование с автоотзывом, наследование ролей, `deny` перекрывает `allow` (ФО §3.5, §6.2).
- Каждое назначение и отзыв роли, права, делегирования, территории — событие журнала (Д-4) с выдавшим, получателем, объектом и причиной.
- Каталог кодов разрешений + автотест «каждый код назначен хотя бы одной роли» (ФО §6.2).
- Подсказки о возможном втором аккаунте (Д-10) начинают адресоваться непосредственному руководителю найденного сотрудника — в уведомлениях и в его карточке. Видны только тем, кто вправе видеть обе карточки.
- Имперсонация — решение Д-19 (ФО §12, вопрос 10).

### 2c. Профили и конфиденциальные слои
- Открытый слой профиля: фото, шапка, должность, подразделение, биография, расширяемый справочник контактов с видимостью каждого поля (всем / региону / коллегам / только руководству), навыки / интересы / языки (ФО §6.3.1). «Коллеги» — сотрудники того же подразделения, включая его руководителя (Д-12).
- **Видимость полей (Д-13):** поле видно, только если его разрешают и права администратора, и выбор владельца. Варианты вложены: «только руководству» (цепочка начальников вверх + руководитель организации) ⊂ «коллегам» ⊂ «региону» ⊂ «всем». «Регион владельца» — ровно территории его подразделения; «региону» видят все, чей территориальный доступ с ними пересекается. Владелец свои поля видит всегда.
- Служебный слой, HR-характеристика, заметки психолога, заметки СБ, заметки «360» — **отдельные сущности** со своими политиками (ФО §6.3.2–6.3.4, ТЗ §16).
- **Заметки «360» (Д-14):** автор выбирает тип при создании — «отзыв» (видят автор, начальник того, о ком заметка, руководитель организации, HR по настройке) или «личная заметка» (видят автор и его руководство). Тот, о ком заметка, исключается всегда, даже если попадает в круг видимости. Тип после создания не меняется. Круг «о ком можно писать» — настройка: своё подразделение (по умолчанию) или любой сотрудник.
- Матрица видимости ФО §8 как стартовая конфигурация.
- Каждый доступ к конфиденциальному слою — событие журнала (Д-4). Массовый экспорт этих слоёв — отдельная привилегия, по умолчанию её нет ни у кого (ФО §6.3.4).
- Просмотр журнала получает области действия: например, руководитель региона видит события только своего региона, если ему это разрешено.

- Заметки «360» (Д-14): отзывы коллег по филиалу друг о друге; личные заметки сотрудника о коллегах; личная заметка сотрудника о собственном начальнике (пример исключения того, о ком заметка); отредактированная заметка с историей правок в журнале.
- Проекты: с этапами и зависимостями — для Гантта; без этапов; созданный из шаблона. Разные health-статусы.
- Задачи: минимум по одной в каждом статусе ФО §6.8.4; просроченные; заблокированная с причиной; с несколькими исполнителями; с трёхуровневыми подзадачами; с чек-листами; повторяющаяся; с записями времени; с перепиской в чате обсуждения.
- Задача «связаться с кандидатом», предметом которой является кандидат без учётной записи, а исполнителем — сотрудник (Д-15); открытая задача деактивированного пользователя с подсказкой о переназначении.
- В журнале — реальные записи, порождённые этими действиями: назначения ролей и территорий, делегирования, переводы, просмотры конфиденциальных слоёв.

### 2f. Сценарные тесты
Проверяются через UI-слой, API, поиск, экспорт и счётчики (ТЗ §52):
- **Своё подразделение vs чужое.** Руководитель филиала A назначает задачу сотруднику A — можно; сотруднику B — запрещено.
- **Территориальная ось.** Руководитель региона Chișinău видит людей и задачи обоих своих филиалов, но не видит Bălți, в том числе в поиске и счётчиках.
- **Подразделение без территории.** HR центрального аппарата получает доступ по оси подразделения, а не по территории.
- **Несколько территорий у подразделения.** Сотрудник «Администрации Север–Юг» видит данные Bălți и Cahul, но не Chișinău.
- **Дополнительная территория.** Сотрудник филиала A с выданным сектором филиала B видит данные этого сектора, но не остальные секторы Кишинёва. После отзыва или истечения срока — снова не видит.
- **Кто может выдавать.** Выдать территорию может непосредственный руководитель или вышестоящий с правом. Рядовой сотрудник и руководитель соседнего филиала — нет.
- **Ограничения выдачи (Д-3):**
  - руководитель филиала A не может выдать сектор филиала B — его собственный доступ не покрывает его; руководитель региона может;
  - назначение без причины не создаётся;
  - назначение со сроком истекает автоматически (тест со сдвигом времени), автоотзыв записан в журнал.
- **Перевод.** Перевод в другое подразделение меняет наследуемый доступ и сохраняет прямые назначения.
- **Второй аккаунт (Д-10).** Подсказку о возможном втором аккаунте сотрудника филиала A видит руководитель филиала A и не видит руководитель филиала B.
- **Непосредственный начальник (Д-11):**
  - новая карточка в филиале получает начальником руководителя филиала;
  - руководитель филиала A меняет начальника своему сотруднику — можно; сотруднику филиала B — нельзя;
  - после смены новый начальник (заместитель) видит служебный слой и HR-характеристику подчинённого, а прежний прямой начальник теряет доступ по этому основанию;
  - смена начальника записана в журнал с тем, кто, когда и с кого на кого;
  - новый руководитель филиала: «неперенастроенные» сотрудники переходят к нему, сотрудник с заместителем-начальником остаётся у заместителя;
  - начальник руководителя филиала — руководитель региональной организации; область «подчинённые» у него покрывает всю цепочку, включая сотрудника заместителя;
  - начальником нельзя назначить сотрудника чужого подразделения;
  - сотрудника нельзя включить во второе подразделение; перевод меняет подразделение, начальника по умолчанию и наследуемые территории, прямые назначения территорий сохраняются.
- **Журнал.** Каждая выдача и отзыв роли, делегирования, территории — запись с выдавшим, получателем, объектом и причиной.
- **Справочник территорий.** После импорта — 1 страна, 6 макрорегионов, 37 единиц, 1684 населённых пункта и сектора; у каждой записи есть названия на ro/ru/en; повторный импорт не создаёт дублей; справочник есть и без демо-мира (как в `production`).
- **Узел «Молдова».** Доступ, выданный на узел «Молдова», покрывает любую территорию страны; доступ на макрорегион «Север» не покрывает Юг.
- **Видимость «коллегам» (Д-12).** Контакт сотрудника филиала A с видимостью «коллегам» видят сотрудники и руководитель филиала A; не видят сотрудники филиала B, региональной организации (родительское подразделение) и люди без подразделения. После перевода сотрудника прежние коллеги этот контакт больше не видят.
- **Видимость полей (Д-13):**
  - поле «только руководству» видят начальник, начальник начальника и руководитель организации; не видят коллеги;
  - поле «коллегам» видит и руководство (вложенность);
  - поле «региону» сотрудника филиала B (сектор Botanica) видят: коллеги по филиалу B, руководство, руководитель региональной организации Chișinău, а также сотрудник филиала A с выданным сектором Botanica; не видят остальные сотрудники филиала A;
  - у сотрудника центрального аппарата (подразделение без территорий) поле «региону» видят только коллеги и руководство;
  - поле, открытое владельцем «всем», но скрытое администратором для роли «Волонтёр», волонтёр не видит — ни в интерфейсе, ни через API, поиск, экспорт или автодополнение;
  - владелец видит все свои поля.
- **Заметки «360» (Д-14):**
  - отзыв о сотруднике филиала A видят автор, руководитель филиала A и руководитель организации; не видят начальники автора, если они не входят в этот круг;
  - личную заметку видят автор и его цепочка начальников; не видит начальник того, о ком она, если он не в цепочке автора;
  - личную заметку о собственном начальнике сам начальник не видит;
  - при настройке «своё подразделение» заметку о сотруднике филиала B создать нельзя; после смены настройки на «любой сотрудник» — можно;
  - тип заметки после создания изменить нельзя;
  - каждый просмотр записан в журнал.
- **Конфиденциальные слои.** Сотрудник не видит собственную HR-характеристику и заметки «360» о себе. HR не видит заметки СБ и психолога. Руководитель организации видит всё. Каждый просмотр слоя оставляет запись в журнале.
- **Делегирование.** И.о. действует до даты окончания; после неё — автоматически теряет права (тест со сдвигом времени). Истёкшее делегирование не даёт прав.
- **Deny.** Явный запрет перекрывает разрешение от другой роли.
- **Каталог прав.** Каждый код назначен хотя бы одной роли.
- **Задачи.** Недопустимый переход статуса отклоняется; просроченность вычисляется, а не хранится.
- **Типы задач (Д-16).** «Поручение» (проверка обязательна) нельзя закрыть из `in_progress` в обход `in_review`; «Звонок» — можно. Деактивированный тип нельзя выбрать для новой задачи, но старые задачи с ним сохраняются.
- **Справочники (Д-16).** Руководитель региона предлагает новый тип задачи — он попадает в очередь, а не в справочник; после одобрения администратором справочников тип доступен всем. Тип, введённый только на русском, сразу получает копию названия на румынском и английском с пометкой «перевод не проверен» и уже доступен для выбора; после правки администратором пометка снимается.
- **Исполнители (Д-15).** Назначить исполнителем или наблюдателем кандидата без учётной записи, заявителя с заявкой на рассмотрении или деактивированного пользователя нельзя; связать кандидата с задачей как предмет — можно.

**Готово, когда:** все сценарные тесты 2f зелёные, конфиденциальные слои недоступны без прав, задача проходит полный цикл статусов с историей. ТЗ прямо требует не идти дальше, пока тесты доступа не проходят (§75, Phase 2).

## Фаза 8 — Обучение и геймификация

### 8.1. Функциональность
- `Course`, `Lesson`, `Quiz`, `QuizQuestion`, `QuizAttempt`, `CourseEnrollment`, `CourseCompletion`: текст, видео, файлы, тесты с автопроверкой; обязательные и добровольные курсы; onboarding-цепочки (ФО §6.12, ТЗ §35).
- `XpEvent`, `Level`, `Achievement`, `Badge`, `Leaderboard`: XP начисляется **только** за подтверждённые доменные события (`TaskCompleted`, `CourseCompleted`, `VisitCompleted`, `EventAttended`); у каждого начисления есть `source_event`, `actor`, `reason`, `amount` (ТЗ §36).
- Лидерборды личные, по региону, по подразделению — с учётом видимости; что из рейтинга публично в профиле — настраивается (ФО §6.12).
- Наставничество: привязка новичка к наставнику, задачи наставника (ФО §6.12).

- **Из прототипа (Д-22) — то, что заказчик называет геймификацией процесса:**
  - **Практические задания урока:** урок сдаётся текстом, файлом, фото или чек-листом; проверяет наставник или руководитель (принять / вернуть на доработку с комментарием). Тесты с автопроверкой остаются.
  - **Клонирование курса** — новый курс на основе существующего.
  - **Массовые задания:** одно задание на аудиторию (сегмент или фильтр); у каждого получателя своё выполнение, сдача и проверка; можно требовать подтверждение (фото, файл); награда в XP начисляется после проверки. Отличие от массовых задач фазы 3: там создаётся по задаче на человека-предмет, здесь — задание получателям-исполнителям.
  - **Онбординг по стадиям:** приглашён → зарегистрирован → профиль заполнен → вводный курс пройден → практика → проверка наставником → активен. Переход «активен» — по подтверждению наставника. Хранится, кто привёл человека (связь «пригласил» фазы 3).
  - **Правила начисления** настраиваются без кода: за какое событие сколько XP.
  - **Ручная корректировка** баллов руководителем — с обязательной причиной и записью в журнал.
  - **Оспаривание начисления:** участник оспаривает начисление или списание с объяснением; решение принимает руководитель; исход виден участнику.
### 8.2. Демо-данные
- Обязательный онбординг-курс и добровольные курсы; записи на курсы на разных стадиях; прохождения тестов — успешные и проваленные.
- Onboarding-цепочка у кандидата; пары наставник — новичок.
- XP **не вставляется напрямую**: демо-сидер выполняет действия (завершение задач из фазы 2, визиты из фазы 7, посещения мероприятий из фазы 5, прохождение курсов), и XP начисляется событиями. Уровни, значки и лидерборды получаются из этого естественным образом.

### 8.3. Сценарные тесты
- Попытка начислить XP без доменного события невозможна.
- Рейтинг, пересчитанный с нуля по журналу `XpEvent`, совпадает с текущим.
- Региональный лидерборд не показывает людей из чужого региона.

## Фаза 11 — AI

### 11.1. Функциональность
- Подключается только после стабилизации структурированных процессов (ТЗ §75, Phase 12).

- Сценарии ФО §5.8: извлечение данных из входящего сообщения → кандидат в `Person` → лид / обращение; суммаризация длинных веток; помощь в формулировках; модерация.
- Чувствительные данные не отправляются стороннему AI-провайдеру по умолчанию (ТЗ §50). Выбор провайдера — по ответу на вопрос 8 из ФО §12.

- **Из прототипа (Д-22):**
  - **AI-помощники по ролям** — настраиваемый набор (в прототипе 18): у каждого свой промпт, перечень разрешённых действий и полей.
  - **Режимы работы:** «только предложить», «выполнить безопасное действие», «выполнить»; порог уверенности — ниже него результат уходит в **очередь проверки** человеком.
  - **Бюджет** на помощника в месяц и журнал запусков: что спросили, что получили, сколько стоило.
  - **Задача из сообщения, текста или голоса:** AI предлагает задачу, человек подтверждает или отклоняет.
  - **Расшифровка голосовых сообщений** в текст.
  - Все действия AI — только через те же доменные Actions и проверки прав (ТЗ §45); прототипные AI-функции вживую не проверялись, поэтому переносится замысел, а не реализация.
### 11.2. Демо-данные
- Фиктивный AI-провайдер с заранее заданными ответами: демо и тесты не делают внешних вызовов.
- Очередь AI-предложений в разных статусах: принятые, отклонённые, ожидающие; пример отклонённого валидацией результата.

### 11.3. Сценарные тесты
- AI-результат не меняет данные в обход авторизации и валидации.
- При отключённом провайдере остальная система работает без деградации.
